1. Project overview

What PolyInstall does

PolyInstall turns a YAML manifest into one or more self-contained installer binaries. It is designed for product teams, open-source maintainers, and internal platform engineers who need a repeatable packaging flow without adopting a different installer authoring system for every operating system.

Current project state The repository is at v2.3.0 and uses Avalonia 12 for the installer wizard. The release pipeline publishes self-contained CLI zips for win-x64, linux-x64, and osx-arm64. Each CLI zip carries the wizard stub, the silent stub, and (on Windows) the uninstall stub for its own RID; separate stubs-<rid> archives are available when you need to build installers for another target. Every release is smoke-tested end to end on Windows, Linux, and macOS before it is published.

How to use PolyInstall

  1. Write a YAML manifest that describes product metadata, targets, wizard steps, and payload files.
  2. Point your editor at the published schema so typos and shape errors show up while you edit.
  3. Run polyinstall validate to collect schema and semantic issues in one pass.
  4. Run polyinstall build to produce installer binaries (and optional AppImage/DMG packaging).
  5. Ship the generated installer. In wizard mode the user walks through the Avalonia wizard; in silent mode (or with --silent) the installer runs unattended from a terminal, script, or deployment tool. Either way it copies files, runs tasks, registers services and associations, and records state for update, repair, and uninstall.

Think of the manifest as the single source of truth. The CLI packages it with your payload; the runtime installer reads the embedded manifest at install time. You do not maintain separate NSIS, Inno Setup, or platform-specific project files for each OS.

What's new in v2.3.0
  • Silent installs: set ui.mode: silent to build with a UI-less stub that is about 9 MB smaller, or pass --silent to any wizard installer. Unattended runs support --install-dir, --features, --accept-eula, --close-apps, --log, and documented exit codes.
  • Windows elevation for silent installs now waits for the elevated child and forwards its exit code.
  • Cancelling a fresh install (wizard or silent) offers or runs a cleanup of the partially copied files.
  • SVG logos are converted to PNG at build time, so the installer stub no longer carries an SVG renderer.
  • macOS stubs are thinned to a single CPU architecture, making osx-* installers smaller.
  • Validation can now emit warnings (warning[PIxxx]) as well as errors; warnings do not fail a build.

See release notes for v2.2.0, v2.1.1, and earlier changes.

2. Prerequisites

Before you install

The recommended path is to download a release build of the CLI. Release archives are self-contained, so users do not need the .NET SDK just to build installers from manifests.

For normal use

  • A 64-bit host OS that matches the downloaded CLI archive.
  • A YAML manifest describing your application.
  • A payload directory containing the files you want to install. It can be built with any language or toolchain.
  • The included host RID stubs, a downloaded stubs-<rid> archive, or a custom stubs/ directory.
  • mksquashfs from squashfs-tools on a Linux host for AppImage output.
  • hdiutil on a macOS host for DMG output.
  • On Linux build hosts that convert an SVG ui.logo_path: libfontconfig and libfreetype (present on most desktop distributions and GitHub's Ubuntu runners, often missing in slim containers).

For source builds

  • .NET SDK 10.x, aligned with the repository target framework. This is only needed to build PolyInstall itself, never to build or run your installers.
  • Git for cloning and contributing.
  • lipo (macOS) or llvm-lipo (Linux) when publishing osx-* wizard stubs, so native libraries are thinned to one architecture. Without it, thinning is skipped and the stub is larger.
Target compatibility The finished installer must run on a machine that matches its target runtime identifier. For example, a windows-x64 installer is intended for 64-bit Windows, not Linux or macOS. Installers are self-contained: the target machine does not need .NET, a language runtime, or any other prerequisite to run the installer itself. Your application's own runtime requirements are yours to bundle or document.
3. Installation guide

Install and configure PolyInstall

Use the release build when you want to package an application. Build from source only when contributing, testing unreleased changes, or publishing custom runtime stubs.

Download a release archive

Open the PolyInstall v2.3.0 release and download the archive that matches your build machine, such as polyinstall-win-x64-<tag>.zip, polyinstall-linux-x64-<tag>.zip, or polyinstall-osx-arm64-<tag>.zip. Each CLI archive includes the runtime stub for that same RID; download a separate stubs-<rid>-<tag>.zip archive when you need to build a different target from the same host. Verify downloads against SHA256SUMS.txt, which is published with every release. 

# Example layout after extracting polyinstall-win-x64-<tag>.zip
polyinstall-win-x64/
  polyinstall.exe                      # polyinstall on Linux/macOS
  schema/v1.json
  stubs/
    win-x64/
      PolyInstall.Runtime.exe          # wizard stub (ui.mode: wizard, the default)
      PolyInstall.Runtime.Silent.exe   # silent stub (ui.mode: silent)
      PolyInstall.Uninstall.exe        # Windows only; embedded when register_arp is true

# Optional: extract stubs-linux-x64-<tag>.zip or stubs-osx-arm64-<tag>.zip under the
# same stubs/ root to build those targets from this host:
#   stubs/linux-x64/PolyInstall.Runtime
#   stubs/linux-x64/PolyInstall.Runtime.Silent
# Verify a download (Linux/macOS)
sha256sum --ignore-missing -c SHA256SUMS.txt     # or: shasum -a 256 -c SHA256SUMS.txt

# Confirm the CLI runs
./polyinstall --version

Add the CLI to your shell

Either run polyinstall from the extracted folder or add that folder to PATH. 

# PowerShell example for the current session
$env:PATH = "C:\Tools\polyinstall;$env:PATH"

# Confirm the command is visible
polyinstall validate .\manifest.yaml

Connect your editor to the schema

Add the schema comment to the top of each manifest for completions and validation in YAML-aware editors. 

# yaml-language-server: $schema=https://bolorundurowb.github.io/PolyInstall/schema/v1.json

Build from source

Contributors can build the CLI and publish runtime stubs directly from the repository. Stubs must be published as single-file, self-contained executables; the build rejects multi-file publishes (a sidecar .dll next to the stub) and suspiciously small stubs with a message showing the correct command. 

git clone https://github.com/bolorundurowb/PolyInstall.git
cd PolyInstall

dotnet restore src/PolyInstall.slnx
dotnet build src/PolyInstall.slnx -c Release --no-restore

# Publish the wizard stub, the silent stub, and the Windows uninstaller
dotnet publish src/PolyInstall.Runtime/PolyInstall.Runtime.csproj -c Release -r win-x64 -o stubs/win-x64
dotnet publish src/PolyInstall.Runtime.Silent/PolyInstall.Runtime.Silent.csproj -c Release -r win-x64 -o stubs/win-x64
dotnet publish src/PolyInstall.Uninstall/PolyInstall.Uninstall.csproj -c Release -r win-x64 -o stubs/win-x64

# macOS stubs: universal native libraries are thinned to the RID's architecture automatically.
# Opt out with -p:PolyInstallThinMacNatives=false, or point at a specific tool with -p:PolyInstallLipoTool=llvm-lipo.
dotnet publish src/PolyInstall.Runtime/PolyInstall.Runtime.csproj -c Release -r osx-arm64 -o stubs/osx-arm64

# Build the sample installer
dotnet run --project src/PolyInstall.Cli/PolyInstall.Cli.csproj -- build examples/polyinstall.sample.yaml --base examples --stubs stubs
4. Quick start

Build your first installer

This example packages a tiny application directory and creates a Windows x64 installer. It is intentionally small, so you can validate the full build loop in minutes.

Create a payload directory

Put the files you want to install under a stable source directory. This example uses a single text file. 

mkdir -p hello-payload
printf "Hello from PolyInstall\n" > hello-payload/hello.txt

Create manifest.yaml

The manifest declares metadata, output settings, UI steps, and which files to include. 

# yaml-language-server: $schema=https://bolorundurowb.github.io/PolyInstall/schema/v1.json
metadata:
  name: HelloPoly
  version: 0.1.0
  publisher: Example Ltd

build:
  output_dir: dist
  compression: brotli
  targets:
    - windows-x64
  windows:
    # user scope defaults under LocalAppData and avoids elevation prompts
    install_scope: user
    register_arp: true

ui:
  theme: system
  wizard_steps:
    - type: welcome
      title: Welcome to HelloPoly
    - type: destination
      title: Choose an install location
      default_path: "{LocalAppData}/HelloPoly"
    - type: progress
      title: Installing HelloPoly
      # defaults to true; set false to hide the detailed log panel
      show_logs: false
    - type: finish
      title: Installation complete

files:
  - source_dir: hello-payload
    include:
      - "**/*"

Validate and build

Run validation first, then build the installer. Output files are written under build.output_dir, relative to --base. 

polyinstall validate manifest.yaml --base .
polyinstall build manifest.yaml --base .

Run the installer

Launch the generated binary on a matching target machine. With the sample above, the destination step defaults under {LocalAppData}/HelloPoly, the progress step shows status (logs hidden because show_logs is false), files are copied, install state is recorded, and the finish step summarises the result. If you add linux-x64 or osx-arm64 to build.targets, the outputs have no extension; mark them executable after downloading. 

# Windows output
dist/HelloPoly-windows-x64.exe

# Linux / macOS outputs (when those targets are added)
chmod +x dist/HelloPoly-linux-x64
./dist/HelloPoly-linux-x64

# Prefer no wizard? Run the same installer unattended (PowerShell; -Wait because the
# wizard stub is a GUI-subsystem app on Windows)
Start-Process .\dist\HelloPoly-windows-x64.exe -ArgumentList '--silent' -Wait
5. Advanced usage and features

Use the full manifest surface

PolyInstall supports multi-target builds, platform-specific packaging, wizard customisation, silent installs, optional features, background services, lifecycle tasks, glob filtering, custom output names, optional signing, environment variable substitution, and install-state tracking for update, repair, and uninstall.

Multi-platform targets

A single manifest can build installers for Windows, Linux, and macOS. Platform options let you enable Add/Remove Programs registration, AppImage packaging, or DMG creation where the host supports it.

Wizard UI and branding

Configure the wizard sequence, select light, dark, or system theme mode, and provide a logo path resolved from the extracted payload at install time. Raster logos (PNG, JPEG, and so on) are used as-is; SVG logos are converted to PNG when you build.

Silent and unattended installs

Set ui.mode: silent for a smaller UI-less installer, or pass --silent to a wizard installer. Scripts get stable exit codes, a timestamped log, and flags for the install directory, features, licence acceptance, and closing running apps. See Silent installs.

Optional features

Declare top-level features and gate files, tasks, file associations, and services on them. Users pick features on the wizard's features step; silent installs use --features.

Services and daemons

Register Windows services, Linux systemd units, and macOS launchd jobs. Services are registered after files are copied, refreshed on update (services dropped from the manifest are removed), and stopped and removed automatically on uninstall.

Lifecycle tasks

Run install-phase actions such as shortcuts, registry writes, desktop entries, permission changes, and PATH updates. Uninstall phases accept file_association (which unregisters the association).

Update, repair, and uninstall

Install state is written under .polyinstall/. Running a newer installer updates in place, running the same version repairs, and the Windows uninstaller removes payload files, services, PATH entries, associations, and the Add/Remove Programs entry. See Install lifecycle.

Running-app detection

Before copying files, the installer checks for processes running from the install location. The wizard offers to close them; silent installs stop with exit code 4 unless --close-apps is passed.

Complete multi-platform manifest

This manifest demonstrates advanced build options, glob filtering, environment substitution, branding, optional features, a feature-gated background service, and OS-gated tasks. The application itself can be written in anything; ContosoStudio here stands for whatever executable your payload ships. 

# yaml-language-server: $schema=https://bolorundurowb.github.io/PolyInstall/schema/v1.json
metadata:
  name: Contoso Studio
  version: "${APP_VERSION:-1.0.0}"
  id: com.contoso.studio
  publisher: Contoso Ltd

build:
  output_dir: dist
  output_name: "{name}-{version}-{target}"
  compression: brotli
  targets:
    - windows-x64
    - linux-x64
    - osx-arm64
  windows:
    # user scope defaults under LocalAppData (no elevation)
    install_scope: user
    register_arp: true
  linux:
    package: appimage
  macos:
    package: dmg
  signing:
    windows:
      certificate_path: "${WINDOWS_CERT_PATH}"
      certificate_password_env: WINDOWS_CERT_PASSWORD
      timestamp_url: "http://timestamp.digicert.com"
    macos:
      identity: "Developer ID Application: Contoso Ltd"
      keychain: "${MACOS_KEYCHAIN_PATH}"
      notarization_profile: "polyinstall-notary"

ui:
  mode: wizard            # default; use "silent" for a UI-less installer
  theme: system
  logo_path: "branding/contoso-logo.svg"   # converted to PNG at build time
  wizard_steps:
    - type: welcome
      title: Welcome to Contoso Studio
    - type: eula
      title: Licence agreement
      source: "legal/LICENCE.txt"
    - type: destination
      title: Choose where to install
      default_path: "{LocalAppData}/Contoso Studio"
    - type: features
      title: Choose components
    - type: progress
      title: Installing
      # omit show_logs or set true to keep the scrolling detail log
    - type: finish
      title: Ready to launch

features:
  - id: samples
    name: Sample projects
    description: Example projects to explore Contoso Studio.
    default_selected: true
  - id: sync_agent
    name: Background sync agent
    description: Keeps projects in sync while Contoso Studio is closed.
    default_selected: false

files:
  - source_dir: app
    include:
      - "**/*"
    exclude:
      - "**/*.pdb"
      - "**/*.map"
      - "**/tmp/**"
  - source_dir: packaging
    include:
      - "branding/**"
      - "legal/**"
  - source_dir: samples
    include:
      - "**/*"
    features: [samples]

services:
  - name: com.contoso.studio.sync
    require: os.isLinux
    scope: user
    description: "Contoso Studio sync agent"
    executable: "{AppDir}/contoso-sync"
    arguments: ["--watch"]
    working_directory: "{AppDir}"
    restart: on-failure
    start: true
    features: [sync_agent]

file_associations:
  - extension: ".cstudio"
    description: "Contoso Studio project"
    prog_id: "ContosoStudio.Project.1"
    icon: "{AppDir}\\branding\\contoso.ico"
    command: '"{AppDir}\\ContosoStudio.exe" "%1"'
    mime_type: "application/x-contoso-studio"
    bundle_path: "{AppDir}/Contoso Studio.app"

tasks:
  pre_install:
    - require: os.isWindows
      action: write_registry
      parameters:
        key_path: "HKCU\\Software\\Contoso\\Studio"
        value_name: InstallStarted
        value: "true"
        value_kind: string
  post_install:
    - require: os.isWindows
      action: create_shortcut
      parameters:
        target_path: "{AppDir}\\ContosoStudio.exe"
        name: "Contoso Studio"
        location: desktop
        description: "Launch Contoso Studio"
        icon_path: "{AppDir}\\branding\\contoso.ico"
    - require: os.isWindows
      action: add_to_path
      parameters:
        path: "{AppDir}"
        scope: user
    - require: os.isLinux
      action: create_desktop_entry
      parameters:
        file_name: "contoso-studio.desktop"
        name: "Contoso Studio"
        exec: "{AppDir}/ContosoStudio"
        icon: "{AppDir}/branding/contoso.png"
        comment: "Launch Contoso Studio"
    - require: os.isUnix
      action: set_permissions
      parameters:
        path: "{AppDir}/ContosoStudio"
        mode: 755
  # Uninstall phases accept only file_association, which unregisters the association.
  # Files, services, PATH entries, top-level file_associations, and the Add/Remove
  # Programs entry are cleaned up automatically.
  pre_uninstall: []
Uninstall phases are not install phases create_shortcut, write_registry, create_desktop_entry, set_permissions, and add_to_path are not valid in pre_uninstall or post_uninstall. polyinstall validate reports PI204. Only file_association is valid there. Files, services, PATH entries, and associations are removed automatically.

Shortcut and file association behaviour

Shortcut names are display names, not full destination paths. PolyInstall chooses the correct desktop or Start Menu directory from location and optional subfolder, then combines it with name. On Windows, .lnk is appended automatically when name does not already end with it; name: "Contoso Studio" and name: "Contoso Studio.lnk" both produce a single Contoso Studio.lnk file. Prefer omitting .lnk in manifests so the same task reads naturally on Linux and macOS. 

tasks:
  post_install:
    - require: os.isWindows
      action: create_shortcut
      parameters:
        target_path: "{AppDir}\\ContosoStudio.exe"
        name: "Contoso Studio"        # Do not include .lnk unless you need to be explicit.
        location: start_menu          # start_menu or desktop
        subfolder: "Contoso"
        description: "Launch Contoso Studio"
        icon_path: "{AppDir}\\branding\\contoso.ico"
Do not package generated shortcuts Do not include .lnk, .desktop, or symlink shortcut files in your files payload just to place launchers on the user's machine. Include the real executable and icon assets, then create launchers with create_shortcut or create_desktop_entry. This keeps uninstall state accurate and lets PolyInstall place shortcuts in the correct per-user or machine-wide location.

Where shortcuts land

Windows: start_menu is the Start Menu Programs folder and desktop is the desktop — per-user for install_scope: user, all-users for machine. Linux: start_menu is ~/.local/share/applications. macOS: start_menu is ~/Applications. On Linux and macOS, shortcuts are symlinks (or a small launcher script where symlinks are unavailable), and an existing file at that path is restored if creation fails.

Shortcuts are not tracked for uninstall

Uninstall removes everything under the install directory, but shortcuts, desktop entries, and registry values created by tasks live outside it and are left in place today. Point shortcuts at files inside {AppDir} so a stale shortcut is harmless, and document manual clean-up if it matters to your users.

File associations should normally be declared with top-level file_associations entries. Use a leading dot in extension, choose a stable prog_id that will not change between releases, include the icon file in your payload, and quote %1 in the open command so paths with spaces work correctly. If prog_id is omitted, PolyInstall derives one from the app name and extension, but explicit values are clearer for long-lived products. 

file_associations:
  - extension: ".cstudio"
    description: "Contoso Studio project"
    prog_id: "ContosoStudio.Project.1"
    icon: "{AppDir}\\branding\\contoso.ico"
    command: '"{AppDir}\\ContosoStudio.exe" "%1"'
    mime_type: "application/x-contoso-studio"     # Linux; optional if the derived type is fine.
    bundle_path: "{AppDir}/Contoso Studio.app"    # macOS; required for macOS associations.

Use the file_association task action only when an association must be created conditionally in a lifecycle phase. Top-level associations are easier to read, participate in feature selection, and are registered after files are copied.

Platform packaging notes

Windows ARP

With register_arp: true (the default), PolyInstall embeds the uninstall host, copies it to Uninstall.exe at the install root, and registers the app in Add/Remove Programs under HKCU or HKLM, including a quiet uninstall command. If registration fails, the copied uninstaller is removed again so no orphaned entry is left.

Linux AppImage

Set build.linux.package: appimage. AppImage creation must run on Linux with mksquashfs available on PATH. The first PNG in ui.assets is used as the AppImage icon.

macOS DMG

Set build.macos.package: dmg. DMG creation requires macOS because PolyInstall invokes hdiutil.

Optional installer signing

Signing is opt-in. If build.signing is omitted, PolyInstall produces unsigned installers. If you configure a platform signing block, the build validates that the required identity reference is present and signs only the matching platform artifacts. Do not put plaintext private keys or account passwords in YAML.

Windows signing

Windows uses signtool from PATH or tool_path. Configure exactly one identity source: certificate_path, certificate_thumbprint, or certificate_subject. Certificate passwords must come from certificate_password_env.

macOS signing and notarisation

macOS uses codesign with an identity. DMG builds can also use an Apple notarytool keychain profile through notarization_profile; PolyInstall submits and staples when that profile is configured. Linux signing is not built in. 

build:
  signing:
    windows:
      certificate_thumbprint: "0123456789abcdef..."
      store_name: My
      store_location: current_user
      timestamp_url: "http://timestamp.digicert.com"
    macos:
      identity: "Developer ID Application: Example Corp"
      keychain: "${MACOS_KEYCHAIN_PATH}"
      notarization_profile: "polyinstall-notary"

  output_dir: "${DIST_DIR:-dist}"

6. Silent installs

Install without the wizard

Silent installs run from a terminal, script, configuration-management tool, or software-deployment system with no window and no prompts. Progress is printed as timestamped lines, written to a log file, and the process exits with a documented exit code.

Option 1: ui.mode: silent

The build uses PolyInstall.Runtime.Silent, a console stub with no Avalonia or Skia code. Installers are roughly 9 MB smaller and are always silent; --silent is implied. Choose this for server software, agents, CLIs, and anything deployed by automation.

Option 2: --silent on a wizard installer

Keep the default ui.mode: wizard for people who double-click, and let administrators pass --silent (or /S, /silent) for unattended runs. One installer serves both audiences. 

ui:
  mode: silent            # "wizard" (default) or "silent"
  wizard_steps:
    - type: destination
      default_path: "{LocalAppData}/Contoso Agent"   # used when --install-dir is not given
    - type: progress

Command-line options

Options are case-insensitive. Unrecognised arguments are rejected with exit code 2, so typos never silently change behaviour.

Option What it does Notes
--silent, /S, /silent Run without the wizard. Required for wizard-mode installers; implied for ui.mode: silent.
--install-dir <path> Install into this directory. Must be absolute with no . or .. segments and no control characters. Ignored when the product is already installed: updates and repairs always use the existing location.
--features <list> Choose optional features. Comma-separated feature ids (samples,sync_agent), all, or default. Omitted or default uses default_selected on a fresh install, or the previously installed selection on update. Unknown ids fail with exit code 2.
--accept-eula Accept the licence non-interactively. Required whenever ui.wizard_steps contains an eula step; otherwise the run exits with code 6.
--close-apps Terminate processes running from the install directory, then continue. Without it, a running copy of the app stops the install with exit code 4.
--log <path> Write the timestamped log to this file. Must be absolute, must not already exist, and must not resolve through a symlink; its folder must exist. When omitted, the log goes to install.log in a new private polyinstall-log-<random> folder under the system temp directory, and the path is printed at start-up.
--help, -h, /? Print usage and exit codes, then exit 0. Nothing is extracted or installed.

How the install directory is chosen

  1. An existing install of the same product (found through install state or, on Windows, Add/Remove Programs) — updates and repairs never move.
  2. --install-dir.
  3. The default_path of the manifest's destination step, with placeholders expanded.
  4. The built-in default: {LocalAppData}/<name> for Windows user scope, otherwise {ProgramFiles}/<name> (C:\Program Files, /usr/local, or /Applications).

If the chosen directory already holds install state for a different product, the run stops with exit code 7 rather than overwrite it.

Exit codes

Code Meaning Typical fix
0Install, update, or repair completed (or --help was shown).—
1Unexpected error.Read the last lines of the log for the error message.
2Invalid arguments: unknown flag, bad path, unknown feature id, unusable log path, or no install directory could be resolved.Correct the command line; run with --help.
3Elevation was needed but was denied, unsupported, or failed.Accept the UAC prompt on Windows, or re-run under sudo on Linux/macOS for system-scope services.

Elevation

On Windows, a silent install that needs administrator rights — install_scope: machine, a Windows service, or updating an existing machine-wide install — relaunches itself through UAC, waits for the elevated copy to finish, and returns its exit code. The elevated copy appends to the same log file, so one log covers the whole run. On Linux and macOS, PolyInstall never escalates by itself: if a system-scope service is involved and the installer is not running as root, it exits with code 3 and asks you to re-run under sudo.

Examples

# Linux / macOS: per-user install with all features and a known log path
./ContosoAgent-linux-x64 --install-dir "$HOME/.local/share/ContosoAgent" \
  --features all --log "$HOME/contoso-install.log"
echo "exit code: $?"

# System-scope service on Linux: run as root
sudo ./ContosoAgent-linux-x64 --install-dir /opt/contoso-agent --accept-eula
# Windows, silent stub (ui.mode: silent) — a console app, so exit codes flow directly
.\ContosoAgent-windows-x64.exe --install-dir "C:\Tools\ContosoAgent" --close-apps
$LASTEXITCODE

# Windows, wizard stub with --silent — a GUI-subsystem app, so wait for it explicitly
$p = Start-Process .\ContosoStudio-windows-x64.exe `
  -ArgumentList '--silent', '--features', 'default', '--accept-eula' -Wait -PassThru
$p.ExitCode
Silent mode and licences If your manifest includes an eula step and sets ui.mode: silent, validation warns (PI145) because every unattended run will need --accept-eula. That is often the right choice for commercial licences; remove the step if unattended deployment should not require it.
7. Install lifecycle

Install, update, repair, cancel, and uninstall

Every successful run writes state under <install-dir>/.polyinstall/. That state is what lets the next installer recognise an existing install, upgrade it in place, and lets the uninstaller remove exactly what was installed.

Product identity

PolyInstall identifies a product by metadata.id when set (a GUID, or any stable string that is hashed into one), otherwise by metadata.name plus metadata.publisher. Changing these between releases makes the new installer treat the product as unrelated, so it installs side by side instead of updating. Set metadata.id before your first public release and never change it.

What the installer does on each run

Situation Mode Behaviour
No existing install found Install Copy core files and selected features, run tasks, register associations and services, write state.
Same product, different metadata.version Update Install into the existing location, keep the previous feature selection as the starting point, remove files and services that are no longer part of the payload, then register the new version.
Same product, same version Repair Re-copy files and re-run registration to restore a damaged install.

Versions are compared for equality only: any different version string is treated as an update, including an older one.

Install order

  1. Check for processes running from the destination (see below).
  2. Run tasks.pre_install.
  3. On update, remove services registered by the previous version that the new manifest no longer declares.
  4. Copy allowed payload files (core plus selected features); on update, prune files no longer in the payload.
  5. Run tasks.post_install.
  6. Register top-level file_associations and services.
  7. Write .polyinstall/install-state.json and embedded-manifest.json; on Windows, copy Uninstall.exe and register Add/Remove Programs when enabled.

Running applications

Overwriting a running executable fails on Windows and can corrupt an app on any OS, so before copying files the installer looks for processes whose executable lives under the install directory. The wizard lists them and offers Close applications and continue or Cancel; if any cannot be closed, setup stops before touching the disk. Silent installs exit with code 4 unless --close-apps is passed. Processes the installer cannot inspect (for example, other users' elevated processes) are skipped.

Cancelling

Fresh install

If files were already copied, the wizard offers Run cleanup, and silent installs clean up automatically. A directory the installer created is removed entirely; in a pre-existing directory only the copied payload files, PolyInstall state, and any Add/Remove Programs entry are removed.

Update or repair

The existing install is left in place, not deleted. Run the installer again to finish the update or repair.

Uninstall

On Windows with register_arp: true, users uninstall from Settings › Apps or Control Panel, or you can run Uninstall.exe from the install root yourself. The installer itself does not accept --uninstall. 

# Interactive uninstall
& "$env:LOCALAPPDATA\Contoso Studio\Uninstall.exe" --uninstall

# Quiet uninstall (also registered as the ARP QuietUninstallString)
& "$env:LOCALAPPDATA\Contoso Studio\Uninstall.exe" --uninstall --quiet

The uninstaller, in order:

  1. Requests elevation if system-scope Windows services were registered.
  2. Runs tasks.pre_uninstall then tasks.post_uninstall (only file_association is allowed there).
  3. Unregisters top-level file_associations for the installed features.
  4. Stops and removes registered services.
  5. Removes PATH entries added by add_to_path.
  6. Removes the Add/Remove Programs entry.
  7. Deletes everything under the install root, then the root itself.
Keep user data out of the install directory Uninstall deletes the whole install root, including files your application created there after install. Store settings, caches, and documents in the user's profile or data folders, not beside the executable.

Safety guards

Uninstall refuses to run when the recorded product id does not match the embedded manifest, and refuses to delete a drive root, the user profile, the Windows or system folders, Program Files, or ProgramData, even if install state points there.

Linux and macOS

There is no bundled uninstaller for Linux or macOS yet. Install state is still written, so a later release can pick it up. Until then, stop any services you registered and delete the install directory; document this for your users if your app registers services or associations.

Install state files

File Contents
.polyinstall/install-state.jsonProduct id, name, version, publisher, install location and scope, payload file list, selected features, registered services, PATH additions, association backups, and the Add/Remove Programs key.
.polyinstall/embedded-manifest.jsonThe manifest the installer was built with, used for uninstall and future updates.
Uninstall.exeWindows only, when register_arp is true.

Treat .polyinstall/ as owned by PolyInstall: do not ship files under that path in your payload (the build rejects the reserved uninstaller path) and do not edit it by hand.

9. Schema reference

Manifest options in detail

PolyInstall manifests are YAML documents that validate against the published schema at https://bolorundurowb.github.io/PolyInstall/schema/v1.json. Think of a manifest as the recipe for your installer: it names the product, chooses where output files go, describes the installer screens, selects the files to copy, and optionally runs setup tasks.

Recommended schema header Add this comment to the top of a manifest to enable YAML language server completion and validation. 
# yaml-language-server: $schema=https://bolorundurowb.github.io/PolyInstall/schema/v1.json

Start small

For a first installer, set metadata, build, ui, and files. Leave tasks empty until you need shortcuts, registry values, desktop entries, or permissions.

Use schema keys

Manifest keys use snake_case. Let your editor load the published schema so typos such as outputDir instead of output_dir are visible while you write the manifest.

Paths are relative

Most file paths are resolved from --base or from the extracted payload. If a file is not found, check the command's --base value before changing the manifest.

Validation model The published schema catches field names and basic shapes in YAML-aware editors. The validate and build commands both run schema checks and semantic validation after YAML parsing and environment substitution. Semantic rules cover target names, compression, relative file source directories, non-empty includes, ui.mode, wizard step order, feature references, task parameters and platform predicates, service names and restart policies, machine-scope PATH and registry rules, and signing combinations. Diagnostics are collected across both stages in one run and printed as rustc-style error[PIxxx] or warning[PIxxx] blocks with paths, YAML carets when available, help notes, and a final count. See diagnostic codes.

Root object

The root object groups product metadata, build settings, UI flow, payload selection, optional integrations, and lifecycle behaviour. Use these links when you see a field in a sample manifest and want to understand what it controls.

Option Type What it holds Beginner guidance

build object Controls output location, compression, target platforms, stubs, and platform-specific packaging. Start with one target, then add more targets after the first installer works.
ui object Configures the wizard theme, branding assets, and ordered installer pages. Include welcome, destination, progress, and finish for a normal install wizard.

File path mental model If you run polyinstall build manifest.yaml --base ./release-input and set source_dir: app, PolyInstall scans ./release-input/app. Files are stored in the payload relative to that source directory. source_dir must be relative and must not contain .. Unix permissions An installer built on Linux or macOS stores each payload file's permission bits and restores them on install, so a script marked executable stays executable. Windows has no Unix mode to record, so an installer built on Windows installs files with the target machine's default mode. Add a set_permissions task, with mode written as chmod would accept it (755, 0644), when a file must be executable whatever machine built the installer.

file_associations entries

Top-level file_associations entries register document extensions after installation. They are easier to maintain than platform-specific registry or desktop-database tasks, and they can be gated by optional features in the same way as file groups and tasks.

Option Type What it does Best practice
extension string Document extension to register. Include the leading dot, for example .cstudio.
description string User-facing file type description. Use a readable name such as Contoso Studio project.
prog_id string or null Stable programmatic identifier for the association. Set an explicit value such as ContosoStudio.Project.1 for shipped apps.
icon string or null Icon file for the associated document type. Include the icon in your payload and reference it with {AppDir} or a relative path.
command string Command used when the OS opens a matching file. Quote both the executable path and %1, for example "{AppDir}\App.exe" "%1".
mime_type string or null Linux MIME type. Optional on Linux. If omitted, PolyInstall derives application/x-<extension>.
bundle_path string or null macOS app bundle to update for document support. Required for macOS associations, for example {AppDir}/Contoso.app.
features array or null Optional feature ids that gate the association. Use only when the associated executable or plugin is optional. 
file_associations:
  - extension: ".cstudio"
    description: "Contoso Studio project"
    prog_id: "ContosoStudio.Project.1"
    icon: "{AppDir}\\branding\\contoso.ico"
    command: '"{AppDir}\\ContosoStudio.exe" "%1"'

features entries

features declares optional components. Anything without a features list — files, tasks, file associations, services — is core and always installed. Anything with a list is installed when at least one of its feature ids is selected. Omitting the top-level features block means everything is core, exactly as in manifests written before features existed.

Option Type What it does Guidance
id string Unique identifier referenced by features: [...] elsewhere and by --features on silent installs. Lowercase snake_case, such as sync_agent. Ids must be non-empty and unique (PI110, PI111).
name string Label shown next to the checkbox on the features step. Short and user-facing.
description string or null Supporting text shown with the feature. One sentence on what the user gets.
default_selected boolean Whether the feature is pre-selected on a fresh install. Defaults to true. Set false for large or specialist extras. On update, the previously installed selection wins. 
features:
  - id: docs
    name: Documentation
    description: Install the offline documentation.
    default_selected: true

files:
  - source_dir: app          # core: always installed
    include: ["**/*"]
  - source_dir: docs
    include: ["**/*"]
    features: [docs]         # installed only when "docs" is selected

Referencing an id that is not declared fails with PI112; referencing features when no top-level list exists fails with PI113. The build records which payload files belong to which feature, so updates add and remove feature files correctly when the selection changes.

services entries

services registers background processes with the platform service manager: the Windows Service Control Manager, systemd on Linux, and launchd on macOS. Services are registered after files are copied, refreshed on update, and stopped and removed on uninstall. Every entry needs a require OS predicate (PI184), so write one entry per platform.

Option Type What it does Guidance
require string OS predicate choosing the service manager. os.isWindows, os.isLinux, or os.isMacOS/os.isOSX.
name string Service name; on macOS, the launchd label. Letters, digits, ., _, and - only (PI181). Reverse-DNS names such as com.contoso.agent work everywhere.
display_name string or null Friendly name where the platform distinguishes it (Windows). Optional.
description string or null Service description. Optional.
scope string system (default) or user. Windows supports system only (PI185) and requests elevation for it. On Linux/macOS, system requires running the installer as root.
executable string Path to the program to run. Supports placeholders. Usually under {AppDir}. Required (PI182).
arguments array of strings or null Command-line arguments; each item is one argument. Supports placeholders. For example ["--service", "--port", "8080"].
working_directory string or null Working directory for the process. Supports placeholders. Often {AppDir}.
enabled boolean Start automatically at boot or login. Defaults to true. Set false for services users start on demand.
start boolean Start the service immediately after install. Defaults to false. Set true when the app expects the service to be running.
restart string or null Restart policy. systemd: no, always, on-success, on-failure, on-abnormal, on-watchdog, on-abort (PI187). launchd: always or on-failure (PI186).
environment map or null Environment variables for systemd and launchd. Values support placeholders. Shell-style names such as APP_HOME (PI188). Do not put secrets here; the manifest is embedded in the installer.
features array or null Feature ids that gate the service. Omit for services that are always installed. 
services:
  - name: ContosoAgent
    require: os.isWindows
    scope: system                      # Windows: system only; triggers a UAC prompt
    display_name: "Contoso Agent"
    executable: "{AppDir}\\contoso-agent.exe"
    arguments: ["--service"]
    start: true
  - name: com.contoso.agent
    require: os.isLinux
    scope: user                        # systemd --user unit; no root needed
    executable: "{AppDir}/contoso-agent"
    working_directory: "{AppDir}"
    restart: on-failure
    environment:
      CONTOSO_HOME: "{AppDir}"
  - name: com.contoso.agent
    require: os.isMacOS
    scope: user                        # ~/Library/LaunchAgents; system uses /Library/LaunchDaemons
    executable: "{AppDir}/contoso-agent"
    restart: always

tasks

Lifecycle task arrays are optional. Install tasks run around file copy. Uninstall tasks run while installed files are still present, but only file_association is accepted there; services, PATH entries, top-level associations, and the Add/Remove Programs entry are cleaned up automatically. A complete novice can ignore tasks until the installer needs to change the system outside the install folder. Tasks run in manifest order and are skipped when their require predicate is false or their features are not selected.

Option When it runs Common use
tasks.pre_install After the running-app check and before files are copied. Write registry values or settings that must exist before files land.
tasks.post_install After files have been copied to the install directory, before services and top-level associations are registered. Create shortcuts, write registry values, create desktop entries, set permissions, or add to PATH.
tasks.pre_uninstall At the start of uninstall, before associations, services, PATH entries, and files are removed. file_association only: unregister an association that was created by a task.
tasks.post_uninstall Immediately after pre_uninstall, still before anything else is removed. file_association only. Despite the name, it does not run after files are deleted.

InstallTask entries

Option Type What it does Beginner guidance
require string or null Optional OS predicate. Supported values include os.isWindows, os.isLinux, os.isOSX, os.isMacOS, and os.isUnix. Use it for platform-specific tasks. Omit it when a task should run on every OS.
action string Task action to run. Supported actions are create_shortcut, write_registry, create_desktop_entry, set_permissions, add_to_path, and file_association. Unknown actions fail with PI160. Choose the action first, then fill parameters with the keys that action expects. In uninstall phases, only file_association is valid.
parameters object or null Action-specific key/value map. String values can use path placeholders such as {AppDir}, {ProgramFiles}, {LocalAppData}, {UserHome}, and {Desktop}. Parameter names are snake_case. The required keys depend on the selected action.
features array or null Optional feature ids that gate this task. Omit for tasks that always run. Set only when the task belongs to an optional feature.

Task action parameters

Action Platforms Typical parameters What it is for
create_shortcut Windows, Linux, macOS target_path, name, location (desktop or start_menu), optional subfolder, description, optional icon_path. Create a user-facing launcher, such as a desktop shortcut.
write_registry Windows only (needs require: os.isWindows) key_path (HKCU\… or HKLM\…, long forms accepted), optional value_name, value, and value_kind (string/reg_sz, expand_string/reg_expand_sz, or dword/reg_dword). 11. Troubleshooting and FAQ

Common issues

Most build failures come from missing stubs, schema mismatches, host-specific packaging tools, or file globs that do not match the intended payload directory.

The build says the stub cannot be found.

Confirm that the resolved stubs root contains stubs/<rid>/PolyInstall.Runtime (or PolyInstall.Runtime.exe) for wizard mode, or PolyInstall.Runtime.Silent (or .exe) for ui.mode: silent. Windows targets with register_arp (on by default) also need stubs/<rid>/PolyInstall.Uninstall.exe. Run polyinstall build --verbose to see which stubs folder was chosen, and check that you extracted the matching stubs-<rid> archive when building for another OS.

The build says the stub is a multi-file publish or is too small.

Installers embed only the stub executable, so it must be published single-file and self-contained. Re-publish with --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true; the error message prints the exact command for your stub.

Do my users need .NET, Node, Python, or anything else to run the installer?

No. Installers are self-contained native executables. Your application may of course have its own runtime requirements; bundle that runtime in the payload or tell users what to install.

A silent install returned a non-zero exit code.

Look the code up in the exit code table, then read the end of the log; its path is printed on the first line of output. The most common causes are a missing --accept-eula (6), the app still running (4), and a relative --install-dir or --log path (2).

On Windows, the wizard installer with --silent returns immediately and $LASTEXITCODE is empty.

The wizard stub is a GUI-subsystem program, so shells do not wait for it. Use Start-Process … -Wait -PassThru and read ExitCode, or build with ui.mode: silent, which produces a console program.

Running the new version installed side by side instead of updating.

The product identity changed. Identity comes from metadata.id, or from metadata.name plus metadata.publisher when id is not set. Keep these identical across releases; set metadata.id explicitly to make renames safe.

The installer says applications are running from the install location.

Files cannot be safely replaced while the app is running. Close the app, choose Close applications and continue in the wizard, or pass --close-apps to a silent install.

How do I uninstall on Linux or macOS?

There is no bundled uninstaller for Linux or macOS yet. Stop and remove any services you registered, then delete the install directory. On Windows, use Add/Remove Programs or Uninstall.exe --uninstall.

SVG logo conversion fails on Linux with DllNotFoundException for libSkiaSharp.

The CLI's SVG renderer needs libfontconfig and libfreetype, which slim containers (Alpine, distroless, -slim Debian images) usually leave out. Install fontconfig and libfreetype6 (or your distribution's equivalents), or switch ui.logo_path to a PNG.

My manifest fails schema validation.

Use polyinstall validate manifest.yaml and check that keys use snake_case. Add the yaml-language-server schema comment so your editor catches issues before the CLI runs. The CLI reports schema and semantic errors together using error[PIxxx] blocks, including manifest paths, YAML carets when the location can be mapped, help notes, and a final error count. Fix every listed issue in one pass, then run validation again. Look codes up in diagnostic codes.

Where should a per-user Windows app install by default?

Use build.windows.install_scope: user and set the destination step default_path to "{LocalAppData}/YourApp". That matches PolyInstall's Windows user-scope default root and avoids requesting administrator rights for typical desktop apps.

No files are included in the installer.

Check files[].source_dir relative to --base, then review include and exclude glob patterns. Start with "**/*" and narrow the match once the build works.

AppImage or DMG output is missing.

AppImage output requires a Linux host with mksquashfs. DMG output requires macOS with hdiutil. Cross-building the raw installer binary is separate from host-native packaging.

Windows shortcuts or registry tasks fail.

Check paths after placeholder expansion, confirm the install has sufficient permissions, and remember that install_scope: machine writes to HKLM and requires elevation. For shortcuts, use the current parameters target_path, name, and location; older shortcut_path examples are no longer accepted.

Signing is configured but the build fails.

Signing runs only when build.signing.windows or build.signing.macos is present. Windows needs signtool and exactly one identity source. macOS needs codesign and an identity. Notarisation requires a DMG package and a notarytool keychain profile. Linux signing is not supported in the manifest.

Can I combine machine install scope with PATH changes?

Yes, but only deliberately. add_to_path defaults to scope: user. If you set scope: machine, also set build.windows.install_scope: machine and expect the Windows installer to require elevation.

Can I put secrets in environment variables?

Do not use PolyInstall manifests for runtime secrets. Environment substitution happens before the manifest is embedded in the installer, so substituted values can be inspected from the final binary. Signing passwords are the exception: reference them by name with certificate_password_env, so the value is read only while signing and never embedded.

Uninstall fails with "Task action '…' is not valid in uninstall phase".

polyinstall validate reports this as PI204. pre_uninstall and post_uninstall accept only file_association. Remove other actions from those phases; PATH entries, services, associations, and files are cleaned up automatically.

13. Contributing and support

Help improve PolyInstall

PolyInstall welcomes focused issues, documentation improvements, tests, and implementation changes that keep the manifest contract, generated schema, CLI behaviour, and runtime behaviour aligned.

Report an issue

Open a GitHub issue with the PolyInstall version, host OS, target OS, manifest excerpt, command output, and the smallest payload structure that reproduces the problem.

Open a pull request

Create a branch from master, keep the change focused, add tests for behavioural changes, and update docs, examples, or schema files when the manifest surface changes.

Contributor workflow

git clone https://github.com/bolorundurowb/PolyInstall.git
cd PolyInstall

dotnet restore src/PolyInstall.slnx
dotnet build src/PolyInstall.slnx -c Release --no-restore
dotnet test src/PolyInstall.slnx -c Release --no-build --verbosity normal
